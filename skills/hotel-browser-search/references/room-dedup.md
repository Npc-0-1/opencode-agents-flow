# 房型重复判定

## 问题定义

判断不同 OTA 的房型是否指向同一酒店内同一类物理房间。不同平台可能改写名称、拆分价格包、隐藏政策或混入钟点/长住房型。

## 判断模式

### 实时证据模式

- 默认必须使用 L0/L1 数据；未获取 OTA 当前房型页证据时，不做事实确认。
- 每条房型数据标注 URL/页面、获取时间、可信度。
- 名称、床型、面积、价格、排序只能作为线索。
- 必须结合描述、取消政策、早餐、入住时长、房型类别、页面状态综合判断。
- 禁止写程序化规则、脚本或算法做成批判断。

### 纯语义理解模式

仅当用户明确要求“不联网/纯语义/只看名称和上下文”时使用：

- 只基于房型名称、语义、用户给出的上下文逐案判断。
- 必须写明：`纯语义判断，不等同于事实确认，不能替代实时互联网证据`。
- 不写程序化规则、脚本或算法做成批判断。
- 不能靠单一字段硬判；无法保证时归入 `不确定`。

## 三分法

| 结果 | 使用条件 |
|------|----------|
| 重复 | 房型名称语义、类别、床型、面积、描述、售卖条件等高度一致 |
| 不同 | 房型类别、时长、空间类型、床型/面积/政策等出现明确冲突 |
| 不确定 | 证据不足、单一字段相似、线索互相矛盾或无法保证 |

## 关键线索

| 线索 | 使用方式 |
|------|----------|
| 名称语义 | 只用于候选匹配；同名仍需看描述和售卖条件 |
| 床型 | 强线索；平台翻译可能不一致 |
| 面积 | 强线索；需注意 m²/sqft 换算和四舍五入 |
| 价格 | 弱线索；受税费、取消政策、促销、币种影响 |
| 排序 | 弱线索；只辅助定位候选 |
| 类别/时长 | 关键冲突线索；钟点、过夜、长租必须区分 |

床型、面积、价格的归一化只用于读表和解释，不作为单独结论。

## 必查证据

| 证据 | 作用 |
|------|------|
| 房型描述 | 判断空间、景观、设施、楼层是否一致 |
| 取消政策 | 区分同房型不同价格包 |
| 早餐 | 区分售卖包，不等于不同物理房型 |
| 入住时长 | 区分过夜/钟点/长租 |
| 房型类别 | 类别冲突时优先降为不同或不确定 |
| 页面状态 | 当前展示、未展示、403、空返回都要限定表述 |

## 判断流程

```
输入: OTA_A 房型 + OTA_B 房型
  │
  ├─ 1. 确认模式
  │   ├─ 纯语义/不联网 → 纯语义理解模式
  │   └─ 其他情况 → 实时证据模式
  │
  ├─ 2. 候选线索
  │   ├─ 名称/床型/面积/价格/排序相似 → 候选
  │   └─ 类别/时长/空间类型冲突 → 降置信度
  │
  ├─ 3. 综合核对
  │   ├─ 描述、政策、早餐、时长、类别高度一致 → 重复
  │   ├─ 关键证据明确冲突 → 不同
  │   └─ 单一字段相似或证据不足 → 不确定
  │
  └─ 4. 输出三分法
```

## 页面未展示的表述

- 某 OTA 当前页面显示的房型：标注 `当前已访问页面显示`。
- 某 OTA 当前页面未显示某房型：标注 `未获取(当前已访问页面未显示；未确认是否在售/展示)`。
- 房型总数不同：正常现象，不代表数据错误。
