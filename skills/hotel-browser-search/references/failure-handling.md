# 失败处理经验

示例数据不可复用为事实；实际任务必须实时重新获取。

## 常见失败模式与对策

### 1. 搜索引擎大面积不可用

**现象**：
- Google/DuckDuckGo 直接报传输错误
- Bing CN 虽能访问但返回完全无关的中文内容（飞书、抖音、1688）
- 尝试多引擎均失败，浪费大量轮次

**根因**：网络环境限制，部分搜索引擎被墙或路由异常

**对策**：
```
优先级 1: 直接命中 OTA 平台（不经过搜索引擎）
  - 已知酒店名 → 构造 Trip.com/tiket.com 详情页 URL
  - 已知城市 + 楼宇名 → 构造 tiket.com 搜索 URL

优先级 2: cn.bing.com 作为唯一可用搜索引擎
  - query 避免中文引号、特殊符号
  - 结果必须人工检查相关性（是否被漂移）

优先级 3: 放弃搜索，报告无法获取并要求用户提供信息
  - 不要在第 4 次同类型失败后再尝试
```

**关键教训**：搜索引擎不是搜索互联网的唯一方式。OTA 平台的站内搜索往往更精确，直接构造 URL 比通过搜索引擎跳转更快。

### 2. Bing 搜索结果漂移

**现象**：搜索 "Transpark Juanda Bekasi hotel" 返回飞书下载页、1688 商家中心

**根因**：Bing 将中文 IP 的英文 query 强行路由到中文内容索引

**对策**：
- 尝试 `cc=us`、`setlang=en-us`、`mkt=en-US` 参数（实测无效但值得尝试）
- 用印尼语 query 代替英语 query，部分情况可减少漂移
- 如漂移严重，直接跳过 Bing，从 tiket.com 等印尼本地 OTA 入手

### 3. OTA 平台封锁

**现象**：Traveloka 403、TripAdvisor 403、Expedia 429、OYO 403

**根因**：反爬机制，检测到非浏览器请求

**对策**：
```
不重试 → 从搜索引擎结果摘要提取碎片信息
  - Bing 搜索结果片段含评分、地址、电话摘要
  - 这些碎片只能作为线索，不能单独支撑去重判断
  - 不需要获取完整页面

权衡：完整页面 > 搜索摘要 > 放弃该平台
```

**经验数据**：

| 平台 | 封锁概率 | 摘要可用性 |
|------|----------|------------|
| Traveloka | 高 | 搜索摘要含评分、地址 |
| TripAdvisor | 高 | 搜索摘要含评分、评价数、地址 |
| Expedia | 中 | 搜索摘要可用 |
| Trip.com | 低 | 通常完整页面可获取 |
| tiket.com | 低 | 搜索列表页含电话、评分 |
| Booking.com | 中 | 搜索摘要可用 |
| Agoda | 中 | 经常空返回 |

### 4. 空结果返回

**现象**：Agoda 返回 404、Booking 返回空列表

**可能原因**：
- 当前已访问页面未显示该酒店，需证据限定
- 酒店名在 URL 中被 slugify 后不匹配
- 平台区域限制

**对策**：
1. 尝试不同 query 格式（不带特殊字符、不带品牌后缀）
2. 如果 2 次尝试仍空 → 标注 `未获取(当前L1搜索未命中；未确认是否上架)`，转向其他平台
3. 不要默认"不存在于互联网"——只能说明当前 L1 搜索未获取

### 5. 评分数据撕裂

**现象**：同一酒店 tiket.com 4.7/5 (122条) vs Trip.com 3.9/10 (3条)

**根因**：
- 不同平台的用户群体不同（本地 vs 跨境）
- 评价量差异大时，少量评价不可靠
- 可能包含房型陷阱（3小时 vs 过夜）

**对策**：
- 不取平均分
- 分别报告各平台评分 + 评价数
- 评价量 < 10 的标注为"统计不显著"
- 关注差评的具体内容（是否反映系统性问题）

## 失败重试策略

### 重试决策矩阵

| 失败类型 | 最大重试次数 | 重试间隔 | 失败后动作 |
|----------|-------------|----------|------------|
| 搜索引擎传输错误 | 3 | 立即切换引擎 | 跳过搜索，直连 OTA |
| 搜索结果漂移 | 2 | 换 query 语言 | 标注 Bing 不可用，换策略 |
| OTA 403/429 | 0 | — | 从搜索摘要提取 |
| OTA 空结果 | 2 | 换 query 格式 | 标注当前 L1 搜索未获取，未确认是否上架 |
| Bing 返回不相关 | 2 | 换 query | 放弃搜索引擎路径 |

### 全程不重试的情况

- Google 系列引擎（Google/Google HK/Google Maps）：一次失败即放弃
- 同一 OTA 平台的多次 403：不重试，改从其他平台获取

## 信息缺失的处理

### 分级标注

| 缺失项 | 标注 | 影响 |
|--------|------|------|
| 电话缺失 | `未获取` | 缺少强线索，不能硬判重复 |
| 地址缺失 | `未获取` | 缺少强线索，不能硬判重复 |
| 坐标偏差 > 1km | `坐标不精确` | 降级到 L2/L3 判定 |
| 评分缺失 | `当前已访问页面未显示评分` | 不影响去重 |
| 某 OTA 未命中酒店 | `未获取(当前L1搜索未命中；未确认是否上架)` | 只能说明当前证据不足 |

### 不确定时的输出

```
判定结果: 不确定
原因: 电话未获取、坐标偏差 350m、地址精度不足
已有证据:
  - 同城市 (Bekasi)
  - 同楼宇名 (Transpark Juanda)
  - 同一管理公司 (Big Property) — 品牌别名已确认
缺失信息:
  - 电话（两个酒店均未从互联网获取到）
  - 精确地址（当前只获取到街道名，未获取门牌号）
建议: 补采电话或精确地址后重新判定
```

## 成本控制

### 避免无效搜索

1. 不要用 5 个搜索引擎搜同一个 query —— 1-2 个足够
2. 搜索结果摘要已包含所需信息时，不点进详情页
3. 同一酒店已在一个 OTA 获取完整数据时，不全量采集其他 OTA
4. 去重判断所需的最小信息集：实时网页证据链；电话/地址/坐标只是线索，不能单独判重

### 并行 vs 串行

- 不同 OTA 平台的搜索可并行（互不依赖）
- 同平台不同 query 可并行
- 去重分析必须在搜索完成后（串行，依赖采集结果）

## 经验教训总结

| 教训 | 原因 | 改进 |
|------|------|------|
| 搜索引擎不可用来回试了 6 轮 | 期望搜索引擎总能工作 | 3 次失败直接切换 OTA 直搜 |
| Bing CN 返回中文内容，浪费 4 轮 | 没及时检查结果相关性 | 首个 Bing 结果即检查是否漂移 |
| 反复尝试 Google/DDG | 不知道这些引擎在此环境不可用 | 预先标记为 P3/P4 优先级 |
| Trip.com 3h 房型陷阱未被及时发现 | 只看了评分没看具体差评内容 | 有差评时必须读取差评全文 |
| 坐标 14 位小数被当作精确值 | 未考虑 GPS 精度限制 | 统一截断到 6 位比对 |
