# 酒店重复判断

## 适用边界

判断两个酒店、房源、OTA ID 是否指向同一经营实体。默认使用当前会话实时互联网证据；只有用户明确要求纯语义判断或不联网时，才启用纯语义理解模式。

## 判断模式

### 实时证据模式

- 事实来自 L0（用户提供）或 L1（当前会话实时网页）。
- 每条证据标注 URL/页面、获取时间、可信度。
- 电话、地址、坐标、管理方、房型、图片、近期评价、平台状态、营业状态、名称语义一起看。
- 禁止写程序化规则、脚本或算法做成批判断。

### 纯语义理解模式

仅当用户明确要求“不联网/纯语义/只看名称和上下文”时使用：

- 只基于名称、语义、用户给出的上下文逐案判断。
- 必须写明：`纯语义判断，不等同于事实确认，不能替代实时互联网证据`。
- 不写程序化规则、脚本或算法做成批判断。
- 证据不足时归入 `不确定`。

## 三分法

| 结果 | 使用条件 |
|------|----------|
| 重复 | 名称语义、经营主体、平台状态、房型/图片/评价等多项证据高度一致，能支撑同一经营实体 |
| 不同 | 名称语义、位置/楼宇、经营主体、房型/图片/营业状态等出现明确冲突 |
| 不确定 | 除以上两类外，一律不确定；可附 `疑似关联/需复核` |

## 禁止硬判

- 电话相同不能推出重复。
- 地址相近或相同不能推出重复。
- 坐标接近不能推出重复。
- 管理方或品牌相同只能说明可能关联，不能推出同一酒店。
- 地址/电话很相似但名称差异大或语义关联性低时，优先考虑历史变迁、改名经营、同址换牌、同楼多业主、同楼多房源等；结论只能是 `不确定/疑似关联/需复核`。

## 判断流程

```
输入：酒店 A + 酒店 B
  │
  ├─ 1. 确认模式
  │   ├─ 用户要求纯语义/不联网 → 纯语义理解模式
  │   └─ 其他情况 → 实时证据模式
  │
  ├─ 2. 收集或读取线索
  │   ├─ 名称语义、地址、电话、坐标、管理方
  │   ├─ OTA/官网/地图/近期评价/平台状态
  │   └─ 房型、图片、营业状态
  │
  ├─ 3. 冲突检查
  │   ├─ 名称差异大或语义关联低 → 不确定/疑似关联/需复核
  │   ├─ 同楼、同址、同电话 → 只标线索，继续综合判断
  │   └─ 多项关键事实冲突 → 不同
  │
  └─ 4. 三分法输出
      ├─ 高度相似酒店 → 重复
      ├─ 明显为不同酒店 → 不同
      └─ 其余无法保证 → 不确定
```

## 多源交叉验证

| 维度 | 使用方式 |
|------|----------|
| 电话 | 强线索，需结合其他证据 |
| 地址 | 强线索，需检查同址换牌、同楼多业主、多房源 |
| 坐标 | 辅助线索，注意平台偏移和精度 |
| 管理方 | 说明关联关系，不等于同一实体 |
| 评分/评价量 | 分平台报告，不平均 |
| 房型/图片 | 可增强或削弱判断，但仍需结合上下文 |

单源信息必须标注：

`URL/页面: {平台详情页URL}；获取时间: {YYYY-MM-DD HH:mm}；可信度: L1（唯一来源，未经交叉验证）`
