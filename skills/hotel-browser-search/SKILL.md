# Hotel Browser Search

## 适用主线

1. 酒店房型搜索：从 OTA 采集房型、床型、面积、价格、政策。
2. 房型重复判定：判断跨 OTA 房型是否指向同一物理房型。
3. 酒店重复判断：判断两个酒店/房源 ID 是否指向同一经营实体。

## 信息与判断边界

### 默认：实时证据模式

| 等级 | 来源 | 使用方式 |
|------|------|----------|
| L0 | 用户直接提供 | 可采信，标注为 L0 |
| L1 | 当前会话实时互联网搜索 | 可采信，必须标注 URL/页面、获取时间、可信度 |
| ✗ | 历史会话、记忆、训练知识、未溯源推断 | 不作为事实证据 |

强制规则：
1. 做事实确认、酒店搜索、房型搜索、酒店/房型重复判断时，必须使用 L0/L1。
2. 每条数据行必须标注 `URL/页面`、`获取时间`、`可信度`；来源不能只写平台名。
3. 当前搜索未获取的信息标注 `未获取(当前L1搜索未命中；未确认是否在售/展示)`，不写成“无”或“不存在”。
4. L1 冲突时按 `L0 > 多方交叉验证 > 报告矛盾并降置信度` 处理。
5. 酒店和房型必须逐案判断；禁止写程序化规则、脚本或算法做成批判定。

### 可选：纯语义理解模式

仅当用户明确要求“纯语义判断”“不需要联网”“只看名称/语义/上下文”时启用：
1. 只能基于模型对名称、语义和用户提供上下文的自然语言理解逐案判断。
2. 必须标注：`纯语义判断，不等同于事实确认，不能替代实时互联网证据`。
3. 不得写程序化规则、脚本或算法做成批判断。
4. 输出仍使用三分法：`重复 / 不同 / 不确定`；无法保证时一律 `不确定`。

## 主线一：酒店房型搜索

详见 `references/room-analysis.md`

### 搜索流程

```
Step 1: 确认目标酒店
  ├─ 已知酒店名/地址 → 直连 OTA 详情页
  └─ 仅知楼宇名 → 先搜楼宇名定位酒店 → 再进详情页

Step 2: 逐 OTA 采集房型列表
  ├─ 优先 Trip.com（详情页房型区结构化最好）
  ├─ 其次 tiket.com（搜索列表含房型+价格）
  ├─ 再次 Traveloka（封锁则从搜索摘要提）
  └─ 每次采集标注: URL/页面 + 获取时间 + 可信度

Step 3: 逐房型采集维度
  必采: 房型名称 | 床型 | 价格(原始币种) | URL/页面 | 获取时间 | 可信度
  尽量: 面积 | 取消政策 | 早餐 | 入住人数 | 景观/楼层

Step 4: 房型列表输出
  按模板输出，缺失字段标注"未获取"
```

### OTA 房型数据定位

| OTA | 房型数据位置 | 访问成功率 |
|-----|-------------|-----------|
| Trip.com | 详情页 → "选择房型"区 → 每个房型卡片 | 高 |
| tiket.com | 搜索列表页即含房型名+价格；详情页有完整政策 | 高 |
| Traveloka | 搜索摘要含部分房型；详情页常403 | 中 |
| Booking.com | 详情页 → Room types 区 | 中 |
| Agoda | 详情页 → 房型列表 | 低(常空返回) |

## 主线二：酒店房型去重

详见 `references/room-dedup.md`

### 判定原则

同一酒店在不同OTA的房型列表需要去重对齐：判断"Trip.com 的 Studio Room"和"tiket.com 的 Studio"是否同一物理房型。

```
默认必须实时获取 OTA 最新房型页证据。
床型、面积、价格、名称相似、排序位置只能作为线索。
必须结合房型描述、取消政策、早餐、入住时长、房型类别、页面状态综合判断。
三分法：高度相似房型 → 重复；明显不同 → 不同；其余 → 不确定。
```

### 房型类别标记

每个房型必须标记类别，类别不同通常是重要冲突线索，但仍需结合页面描述、售卖条件和入住时长综合判断：

| 类别 | 识别关键词 | 标记 |
|------|-----------|------|
| 过夜待核 | 未见时长限制线索 | `[时长未确认]` / `[疑似过夜/需复核]` |
| 钟点房 | Transit / Day Use / 3h / 6h / 12h / Hourly | `[钟点]⚠️` |
| 长租 | Monthly / Long Stay / Weekly | `[长租]` |

## 从属任务：酒店去重

详见 `references/dedup-analysis.md`

判定原则：证据驱动、逐案判断。电话、地址、坐标只能作为线索，必须结合官网/OTA/地图/近期评价/平台状态/名称语义/管理方/房型/营业状态等证据综合判断。

三分法：高度相似酒店 → 重复；明显为不同酒店 → 不同；其余无法保证 → 不确定。电话相同、地址相近或相同都不能单独推出重复。

地址/电话很相似但名称差异大或语义关联性低时，考虑历史变迁、改名经营、同址换牌、同楼多业主等，只能输出 `不确定/疑似关联/需复核`。

## 搜索策略

详见 `references/search-workflow.md`

1. **OTA 直搜优先**：直接构造 OTA URL，不依赖搜索引擎
2. **搜索引擎兜底**：`cn.bing.com` 为首选，失败 3 次切换
3. **逐级放松**：精确名 → 楼宇名+城市 → 城市宽搜 → 换OTA → 标注当前 L1 搜索未获取

---

## 失败处理

详见 `references/failure-handling.md`

- OTA 封锁(403/429) → 不重试，从搜索摘要提取
- 空结果 → 按放松策略逐级尝试，最多 2 轮
- 房型数据不完整 → 标注未获取，不编造

## 房型陷阱

详见 `references/room-trap-detection.md`

搜索和输出时必须检查的陷阱：
1. 钟点房伪装过夜房（名称含糊时看价格是否为小时价）
2. 不含税价伪装全包价（价格旁无"含税"标注时默认怀疑不含税）
3. 不可退款价作为默认展示价（OTAs 常默认展示最低价即不可退款价）
